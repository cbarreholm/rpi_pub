# Learnings

## Running Tests
- `pytest` is NOT installed. Always run tests with: `python -m unittest discover -s <test-dir> -p "<test-file>.py" -v`
- Example: `python -m unittest discover -s ansible/roles/os_users/tests -p "test_limited_users.py" -v`
- Running `python -m unittest ansible/roles/os_users/tests/test_foo.py` fails because Python treats the path as a dotted module name and tries to import `ansible.roles...`.
- Running `python -m pytest ...` fails because pytest is not installed.

## Verified Tasks
- Trixie bring-up (2026-05-12, Pi 4B, `has_wifi: true`): Full `prepPiServer.yml` rollout via the Phase 1–6 procedure in `plans/trixie-bring-up-rollout.md` brings up a functional server. eth0 and Wi-Fi both work end-to-end without any manual `nmcli` workaround. Only `--failed` units after Phase 6 are the two known/tracked issues: `exim4.service` (Task 26 — IPv6 socket creation fails because `os_kernel` disables IPv6) and `fail2ban.service` (Task 22 — nginx jails enabled unconditionally on non-nginx hosts). The cloud-init `cc_netplan_nm_patch` warning on Trixie is benign noise — module is referenced but absent in cloud-init 25.2, does not block NM profile rendering. NM keyfiles under netplan are runtime-rendered to `/run/NetworkManager/system-connections/` each boot; `/etc/NetworkManager/system-connections/` is expected to be empty (checking `/etc/` for the profile and concluding it is "missing" is a wrong-place lookup). The earlier "Wi-Fi lost across reboots" symptom on `reverseproxy` is now attributed to `has_wifi: false` blacklisting `brcmfmac`, not a netplan/cloud-init bug.
- Trixie in-place `has_wifi` flip (2026-05-12, Pi 4B): Flipping `has_wifi: true → false` on an already-provisioned host and re-running only `--tags modprobe` + reboot is sufficient — no full re-rollout needed. Result: `brcmfmac`/`brcmutil` blacklisted, `wlan0` absent, `cfg80211` not loaded, `--failed` set unchanged from baseline. nmcli retains the netplan-rendered wifi *connection definition* (it is regenerated from `/etc/netplan/` on every boot regardless of module state), but with an empty `DEVICE` column since there is nothing to bind to — this is expected and not a regression. The Realtek wifi powersaving options written by `os_kernel` (REQ-KRN-06 → `/etc/modprobe.d/disable_wifi_powersaving.conf`) are unconditional and harmless when those modules never load — kernel silently ignores `options` lines for absent modules.
- Task 28: Two certbot var gaps surfaced after Task 27 unblocked the apt step. (1) `nginx_certbot_primary_domain` was never defined — only a commented example in `http_reverse_proxy/vars/main.yml`. Fixed by deriving it from `nginx_certbot_domains` (`{{ nginx_certbot_domains.split(',')[0] | trim }}`) so the cert directory name (`/etc/letsencrypt/live/<primary>/`) can't drift from the first comma-separated domain. (2) `nginx_certbot_email` worked accidentally because the vault used a flat `nginx_certbot_email:` key loaded as a global extra-var that happened to match the role-side reference — fragile if any other role ever defined the same name. Fixed by adopting the established group-prefix vault convention (vault: `http_reverse_proxy_server_nginx_certbot_email`, inventory: `nginx_certbot_email: "{{http_reverse_proxy_server_nginx_certbot_email}}"`). Vault rename is an operator step (`ansible-vault edit ansible/secrets/secrets_file.enc`) — not committed by the playbook. Pattern reaffirmed across the repo: vault entries use `<group>_<varname>`, inventory exposes short alias to the role. Lint side-effect: uncommenting `nginx_certbot_primary_domain` adds 1 to the role-vars `var-naming[no-role-prefix]` count (1 → 2), same rule as adjacent `config_nginx_site_src_dir` and consistent with the existing no-role-prefix pattern; not fixed here (out of scope, see Task spec). Test at `http_reverse_proxy/tests/test_certbot_primary_domain_derivation.py`.
- Task 27: nginx postinst auto-starts via `invoke-rc.d nginx start`, and the stock `/etc/nginx/sites-enabled/default` listens on `[::]:80`. With IPv6 module-blacklisted (Task 25 / REQ-KRN-02), the kernel returns `EAFNOSUPPORT (97)` and the postinst exits non-zero — leaving `nginx` and `python3-certbot-nginx` in dpkg `iU` state and failing the apt task. Fixed in `http_reverse_proxy/tasks/nginx.yml` by wrapping the apt install with a `/usr/sbin/policy-rc.d` shim (`#!/bin/sh\nexit 101\n`, mode 0755) that suppresses the auto-start; the shim is removed immediately after apt. The role's existing "Remove default site" + "Deploy …" + "Restart nginx" handler then brings nginx up with its IPv4-only config. Generalisable pattern for any service whose Debian postinst auto-starts before role config can land — promote to a shared role only if a second consumer appears. Recovering a host already left in `iU`: `sudo sed -i '/listen \[::\]:80 default_server;/d' /etc/nginx/sites-available/default && sudo rm -f /etc/nginx/sites-enabled/default && sudo dpkg --configure -a`. Test at `http_reverse_proxy/tests/test_nginx_install_no_autostart.py`.
- Task 25: Removed the `## IPV6 Networking` and `## IPV6 Disabled` blocks from the sysctl content in `os_kernel/tasks/main.yml`. The modprobe blacklist (`/etc/modprobe.d/ipv6.conf` → `blacklist ipv6`) is now the single source of truth for IPv6 disablement. Rationale: after a reboot following the blacklist taking effect, `/proc/sys/net/ipv6/*` does not exist and `sysctl -p` fails non-zero on those keys. The `copy` task replaces the file wholesale so stale IPv6 lines on already-provisioned hosts are removed automatically. Requirements amended: §1.4 REQ-KRN-07 (dropped "and disabling IPv6"); §2.3 REQ-KRN-06 (replaced sysctl wording with cross-reference to REQ-KRN-02). Test at `os_kernel/tests/test_ipv6_sysctl_removal.py` (8 cases: sysctl content has no `net.ipv6.*` / no `disable_ipv6` / no IPV6 section headers; IPv4 hardening + kernel hardening keys retained; modprobe `Disable IPV6` task still writes `/etc/modprobe.d/ipv6.conf` with `blacklist ipv6`).
